## 1. Goal & Scope
Provide institutional-grade governance, edge-case mitigation, data sanity auditing, and ongoing database maintenance for the quantitative platform adhering to the 00A Canonical Registry.

This phase delivers:
- Corporate-Action Integrity Audit: detects extreme single-bar price moves ($> 25\%$) and cross-references them against the official `corporate_actions` table to isolate unadjusted splits from genuine market crashes.
- Rigorous handling of quantitative market phenomena: survivorship bias disclosures, trading halts, upper/lower circuits, and zero-volume liquidity gaps.
- Automated DuckDB storage maintenance: post-sync `CHECKPOINT` to truncate WAL; weekly Saturday `VACUUM` and defragmentation.
- Disaster Recovery & Automated Backup Drill: exports portable Parquet snapshots weekly and verifies restore viability in an isolated scratch database.
- Reversible schema migrations with automated rollback procedures for `schema_version`.

## 2. SOLID Principles Application
- **Single Responsibility Principle (SRP)**:
  - `DatabaseMaintenanceService`: Responsible solely for executing `CHECKPOINT`, `VACUUM`, and snapshot exports.
  - `DataIntegrityAuditor`: Responsible solely for scanning time-series tables for anomalous ticks, negative prices, and unlinked splits.
  - `DisasterRecoveryManager`: Responsible solely for executing backup validation drills and database recovery probes.
- **Open/Closed Principle (OCP)**:
  - Audit checks implement the `IAuditRule` interface. Registering new integrity rules (e.g. Volume Spike Z-score $> 10$) requires adding a rule class without modifying existing audit loops.

## 3. Quantitative Market Data Edge Cases

### 3.1. Survivorship Bias Mitigation & Mandatory Disclosure
- **The Issue**: Broker historical APIs (including Fyers) provide data only for active, currently tradeable securities. Companies delisted, liquidated, or suspended over the last 15 years are missing from the current master.
- **System Policy**:
  - Every exported file (Parquet, CSV, Excel) and every backtest report generated by the platform must embed the standardized survivorship disclosure:
    `"Data Source: Fyers Active NSE Equity Universe. Note: Historical datasets are subject to survivorship bias for multi-year simulations."`

### 3.2. Corporate-Action Integrity Audit Protocol
Extreme single-bar price shifts can indicate either real market volatility or unadjusted stock splits/bonuses:
1. `DataIntegrityAuditor` scans `candles_1d_raw`:
   $$\Delta P_t = \frac{|Close_t - Close_{t-1}|}{Close_{t-1}}$$
2. If $\Delta P_t > 0.25$ (single-day price shift $> 25\%$):
   - Cross-reference with `corporate_actions`:
     `SELECT * FROM corporate_actions WHERE symbol = $symbol AND ex_date = $date;`
   - **Case A: Corporate Action Found**:
     - Verify that `adjustment_factors` contains a corresponding factor matching the corporate action ratio.
     - Verify that `candles_1d_adjusted` smooths out the price jump ($\Delta P_{\text{adj}} < 0.25$).
   - **Case B: No Corporate Action Found**:
     - Flag as `SUSPICIOUS_PRICE_ANOMALY`. Check if trading volume was exceptionally high (news-driven) or volume was 1 lot (bad tick / illiquid fat finger). Record incident in audit log.

### 3.3. Circuit Breakers, Trading Halts & Zero-Volume Gaps
- **Upper / Lower Price Freezes**:
  - When a stock hits its circuit limit, trades occur only at the limit price with order queues.
  - Valid candles continue to be recorded.
- **Exchange-Wide Market Halts**:
  - Trading halts for 45 to 120 minutes (e.g. March 2020 circuit breaker).
  - **Storage Policy**: Zero synthetic candles are stored in `candles_1m_raw`.
  - **Resampling Policy**: If a higher timeframe bucket (e.g. 15m) falls entirely inside a market halt, resampler produces an explicit bar with `open = close = prev_close`, `volume = 0`, and `is_zero_volume = TRUE`.

## 4. DuckDB Storage Maintenance & Compaction

### 4.1. Write-Ahead Log (WAL) Compaction
During batch insertions, DuckDB appends transactions to `market_data.duckdb.wal`:
- Unchecked WAL growth degrades startup times and consumes unnecessary disk space.
- **Maintenance Policy**:
  - Immediately following each daily incremental sync (Phase 06) or after every 100 symbols during initial backfill:
    Execute SQL: `CHECKPOINT;`
  - This flushes in-memory transaction pages to the main columnar file and truncates `market_data.duckdb.wal` to 0 bytes.

### 4.2. Database Vacuuming & Defragmentation
- Executed weekly via scheduler (Saturdays at 02:00 AM IST):
  Execute SQL: `VACUUM;`
- Reclaims free memory pages, eliminates internal row-group fragmentation, and refreshes DuckDB internal Zone Map min/max statistics for peak query performance.

## 5. Disaster Recovery & Backup Restoration Drill

### 5.1. Hot Parquet Snapshot Export
Every Saturday at 03:00 AM IST:
```sql
EXPORT DATABASE 'data/backups/weekly_snapshot' (FORMAT PARQUET);
```
- Produces vendor-neutral Parquet partitions for every table (`symbols.parquet`, `candles_1m_raw.parquet`, etc.) along with schema DDL files.

### 5.2. Automated Restore Verification Drill (`scripts/run_backup_drill.py`)
Backups are unverified until proven restorable:
1. The backup runner creates an isolated scratch database: `data/scratch/restore_test.duckdb`.
2. Restores snapshot:
   ```sql
   IMPORT DATABASE 'data/backups/weekly_snapshot';
   ```
3. Compares row counts between production and restored scratch database:
   - `SELECT count(*) FROM production.candles_1m_raw` vs `SELECT count(*) FROM restore.candles_1m_raw`.
   - `SELECT count(*) FROM production.symbols` vs `SELECT count(*) FROM restore.symbols`.
4. If row counts match 100%: records `BACKUP_VERIFIED` in `job_logs` and deletes scratch file.
5. If mismatch detected: raises critical alert, preserves scratch database for forensic analysis, and retains previous backup.

## 6. Schema Migration Rollback Protocol
If a migration fails or must be reversed:
1. Migrations under `db/migrations.py` define paired `up()` and `down()` methods.
2. `scripts/rollback_migration.py`:
   - Checks `SELECT version FROM schema_version ORDER BY applied_at DESC LIMIT 1`.
   - Executes migration's `down()` method inside an atomic DuckDB transaction.
   - On success, deletes the record from `schema_version`.
